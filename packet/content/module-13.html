ARP is the glue between Layer 3 and Layer 2, and it is the quiet reason the course teaches both addressing systems. Module 13 has one signature idea that, once you hold it, makes routed forwarding in Module 22 almost obvious: for a remote destination, a host ARPs for its gateway, not for the destination.

The problem ARP solves

A host knows the destination's IP address (from a name lookup, or because you typed it). But an Ethernet frame needs a destination MAC address. Something has to turn one into the other. That something is the Address Resolution Protocol.

How it works

  1. The host checks its ARP cache for the MAC it needs. If it is there, done.
  2. If not, it sends an ARP request: a broadcast to FF:FF:FF:FF:FF:FF that asks "Who has 192.168.10.1? Tell 192.168.10.5."
  3. Every device on the network receives it. Only the owner of that IP answers.
  4. The owner sends an ARP reply as a unicast straight back, saying "192.168.10.1 is at AA:BB:CC:00:00:01."
  5. The asking host stores the answer in its ARP cache and finally sends the real frame.

The shape to remember: request is a broadcast, reply is a unicast. That pairing is a frequent quiz question.

The signature idea: who do you ARP for?

ARP only works within one network, because broadcasts do not cross routers. So a host can only ever ARP for something on its own network.

Read the bold row twice. The frame and the packet inside it are addressed to different devices. The frame goes to the gateway because that is the next stop. The packet inside keeps the real destination IP because that is where it is ultimately going. This is the single most important fact connecting Modules 12, 13, and 22.

The ARP cache

Hosts remember what they learn, so they do not ARP for every frame. Entries are aged out after a few minutes if unused, which keeps the table honest when devices change.

C:\> arp -a                    show the cache on a PC
Interface: 192.168.10.5
  Internet Address      Physical Address      Type
  192.168.10.1          aabb.cc00.0001        dynamic

C:\> arp -d                     clear the cache

Router# show ip arp             the same table on a Cisco router

A good drill: clear the cache with arp -d, run arp -a and see it empty, ping the gateway, then run arp -a again and watch the gateway appear. You have just proved that ARP runs on demand.

Do not confuse this with the switch's MAC address table from Module 7. The ARP cache maps IP to MAC and lives on hosts and routers. The MAC table maps MAC to port and lives on switches. Questions mix them up on purpose.

The security angle

ARP has no authentication. Any device can send a reply claiming to own an address, and hosts will accept it. In ARP spoofing, an attacker answers for the gateway so victims send their traffic to the attacker first. A gratuitous ARP is an unrequested announcement ("this IP is at this MAC"), used legitimately when a device comes up or fails over, and abused by attackers for the same reason it is useful.

IPv6 note

IPv6 does not use ARP. Neighbor Discovery does the same job with multicast instead of broadcast.

Before you move on

  • Say which ARP message is broadcast and which is unicast.
  • For a ping to a host on another network, name the IP and the MAC the frame leaves the sender with.
  • Say what arp -a and show ip arp display, and why each table differs from a switch's MAC table.
  • Explain why an attacker can poison an ARP cache and not an IP routing table.
